# Dependencies

**`pyproject.toml` is the canonical contract.** Everything else in the
repository is either a pinned subset of it or a historical artifact, and this
file says which is which — because the repository briefly had two contracts that
did not know about each other, and the gap between them was invisible until a
clean machine tried to install one and run the other.

## Installing

Two supported ways in, and the difference between them matters.

**Reproducible** — the exact closure, verified by hash. This is what CI's
fresh-clone job runs and what you want when a result has to be reproducible:

```sh
python -m pip install --require-hashes -r requirements.lock
python -m pip install --no-deps -e .
```

`--no-deps` on the second line is not a shortcut. The lock already installed
every dependency at a verified hash; letting pip resolve again would let it
substitute something the lock did not choose. (An editable install cannot itself
be hash-checked, which is why it is a separate line.)

**Working** — resolve fresh against the declared bounds:

```sh
python -m pip install -e ".[all]" -c constraints.txt
```

Either gives the whole repository: the quantitative core, the market-intelligence
collector, the API, plots, cloud sync and the dev tooling.

For a narrower install, pick extras:

| Extra | Brings | Needed for |
|---|---|---|
| *(base)* | numpy, pandas, scipy, statsmodels | `btc_forecaster` core, feature and evaluation logic |
| `models` | prophet, xgboost, scikit-learn, arch | fitting anything; adapters degrade to a clear error without it |
| `data` | yfinance | live market pulls only — never imported by unit tests |
| `plots` | matplotlib | figure artifacts |
| `api` | fastapi, uvicorn, pydantic | `api_server.py` |
| `cloud` | boto3 | S3 artifact sync |
| `market-intelligence` | duckdb, pytz, fastapi, uvicorn, pydantic | `market_intelligence/`, `btc-intel` |
| `dev` | pytest, coverage, ruff, mypy, httpx | running the suites |

### Why `pytz` is declared explicitly

duckdb needs it to hand a `TIMESTAMPTZ` column back as a Python datetime, and
does not declare it itself. Every timestamp in the intelligence corpus is
`TIMESTAMPTZ`, so without it the collector raises on the first read of anything
it has written. It used to reach developer machines only transitively, through
`yfinance` — a quantitative dependency with no relation to collection — so every
machine that had run the quant tracks had it and a clean deployment did not.
That is the shape of bug this file exists to prevent.

## The files, and which one is the authority

| File | Is | Regenerated by |
|---|---|---|
| `pyproject.toml` | **the authority** — what the repository declares it needs | edited by hand |
| `constraints.txt` | the exact versions the committed evidence was produced under | edited by hand, deliberately |
| `requirements.lock` | the full transitive closure of both, with hashes | `bash scripts/lock.sh` |
| `requirements-market-intelligence*.txt` | the collector's frozen deployment subset | edited by hand, mirrored from the extra |

**`requirements.lock`** — the transitive closure: every package that actually
gets installed, pinned exactly, each with the SHA-256 of every artifact that
satisfies it. Generated by `scripts/lock.sh` from `pyproject.toml` with
`constraints.txt` applied as constraints, so it cannot drift away from the
versions the research evidence was produced under — a test asserts it has not.

It is **universal**: one file with environment markers covering Linux, macOS and
Windows, resolved at Python 3.11. 3.11 is deliberate rather than convenient — it
is the floor in `requires-python`, the version both CI jobs use, and the version
in both Dockerfiles. A closure resolved at 3.14 can contain a distribution with
no 3.11 artifact, and that failure would surface on the deployment host instead
of here.

The gap it closes is not theoretical. `constraints.txt` pins 25 packages; the
resolution is 83. The other 58 were reaching every install at whatever version
was current that day, and they include the code that parses the dates
(`python-dateutil`), verifies the TLS (`certifi`, `urllib3`) and schedules the
numerics (`joblib`, `threadpoolctl`).

Never edit it by hand. Change `pyproject.toml` or `constraints.txt`, run
`bash scripts/lock.sh`, and commit the result with the change that caused it.

**`constraints.txt`** — the exact versions the platform was developed and tested
against, for the packages this repository names itself. Not the closure; that is
`requirements.lock`, which is generated from this file and cannot disagree with
it. Its job is to record what the committed evidence under `research/runs/` was
produced under. Bumping a pin here is a separate change that produces its own
evidence, and it requires regenerating the lock in the same commit.

**`requirements-market-intelligence.txt`** and **`-dev.txt`** — the pinned subset
the market-intelligence CI job installs. They are kept, not folded into
`pyproject.toml`, because that job is part of a frozen deployment contract
(`deploy/COLLECTION_FREEZE.md`) and its green history is evidence about the
collector. They must stay consistent with the `market-intelligence` extra; a
test asserts they do.

## Adding a dependency

1. Add it to the appropriate extra in `pyproject.toml`.
2. Pin the tested version in `constraints.txt`.
3. If the collector needs it, mirror it into `requirements-market-intelligence.txt`.
4. Run `bash scripts/lock.sh` and commit `requirements.lock` in the same commit.

A dependency that only ever arrives transitively is not declared, and will be
missing on the one machine that matters.
